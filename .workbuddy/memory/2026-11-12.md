## 缠论图表项目：性能与代码审查（仅分析，未改源码）

- 基线：`node tests/run.js` → 144 passed / 0 failed；CI 为 node 18/20/22 × syntax check + tests。
- 实测（20,000 根 K 线）：全量 `analyze` ~7.5 ms；`updateLast` 仅改收盘价 0.32 ms/tick、改高价触发尾部全量重扫 0.60 ms/tick；`calcDivergences` ~1.02 ms（977 笔 / 125 中枢 / 184 背驰，动量缓存稳态只省约 9%）；`calcSegmentsFull` + `calcCenters` 合计很小，不值得动。
- 最大收益点：`data-layer.js` 的 `createKlineCache.merge` / `normalizeKlines` 每次合并都全量 Map 去重 + 排序。5k 缓存加 1 根 0.768 ms → 有序归并 0.095 ms（8.1x，结果逐字段一致）；20k 缓存 4.29 ms。影响首屏缓存复用、分页、重连回补。
- 次要点：`rebuildFilteredFractals` + `firstDiffIndex` 每 tick 全量；`recalcDivergences` 每 tick 全量遍历笔（可按 dirtyFrom 只重算尾部）；`countSameDirectionCenters` O(k·m) 可前缀和；`buildCenterIndex` 每次分配 cover；`updateStatus()` 在 CHAN indicator calc 里每次写 DOM（footer 有 aria-live）；realtime init 路径 `dataList.slice()` 多余（fullInit 已自建 raw）。
- 一致性隐患：`divergence.js` 的 `centerIncomingDir` 用「笔」判中枢方向，注释称与绘制层 `main.js` 的 `centerDirOf` 同口径，但后者用「线段」，同一中枢的背驰类型判定与图上着色可能不一致。
- momCache 实测不是泄漏：追加 20k 根后 500 outer / 903 inner 键；5000 次 updateLast 键数不变（稳态不增长），但长期追加会线性累积，可加裁剪。
- 基准脚本（临时，非项目文件）：`C:/Users/qiaow/AppData/Local/Temp/chanlun-bench.js`、`chanlun-bench2.js`。第二个用依赖注入包装 `core.divergence.calcDivergences` 拦截 analyzer 内部 momCache，无需改源码。
- 结论：当前规模无性能瓶颈，优化属于规模化余量与首屏/分页延迟，不是修卡顿。若实施，建议从有序归并开始（收益最大、风险最低、有等价性验证）。
